1What this system does

1.1The problem it solves

Most things that embarrass a web team on launch day are not subtle. A link to a page that was renamed. A hero image that 404s only on the live host. The previous client's name still in the footer because the site was cloned from theirs. A contact form that silently disappeared in a refactor. A layout that scrolls sideways on a phone.

All of those are mechanically detectable, and all of them are routinely missed because checking them by hand across five viewports and twenty pages is tedious work that gets skipped under deadline. This system does that work on every push, in about eight minutes, and refuses to let a broken build reach production.

1.2What it checks — and what it does not

It does not read your .astro source files. It builds the site, serves the production output, and drives a real browser over the rendered pages across Chromium, Firefox and WebKit.

That distinction matters. A linter reads your components; this reads the website your client will see. It will not tell you a component is badly structured. It will tell you that the structure produced a page with no H1, a stretched logo and 1,441 pixels of horizontal overflow at mobile width.

Thirty-four checks run in seven modules. Appendix A lists all of them. In summary:

ModuleCovers
Pages & SEORequired pages load, the custom 404 page is intact, title / meta description / H1 / viewport / lang, accidental noindex, canonical and Open Graph, heading hierarchy, robots.txt, sitemap, browser runtime errors
IdentityForbidden business names anywhere on the page, expected business name present, phone and email in both visible text and tel:/mailto: links, privacy policy exists and is linked, logo links to the homepage
FormsA form exists on every page that needs one (native, GoHighLevel/LeadConnector, HubSpot or other iframe embeds), required fields present, accessible labels, a submit button, and no wrong company name inside the form region
LinksInternal links resolve including soft-404 detection; external links reachable, with rate-limited hosts skipped rather than failed
ImagesFailed loads, zero natural size, broken background images, stretched aspect ratios, missing alt, file-size budget, lazy loading below the fold
LayoutHorizontal overflow, disappearing elements, clipped text and element overlap at five viewports, container width and page gutters, optional screenshot regression
Interaction & a11yMenus, modals, dropdowns and drawers open and close and stay keyboard reachable; hover and focus states produce a visible change; axe-core WCAG 2.1 A/AA scan
PerformanceLighthouse CI on key pages with configurable thresholds
Design principle

Checks that cannot be inferred from the site — brand colour rules, element-overlap pairs, visual-regression baselines — ship disabled. Turning them on is a deliberate decision you make once a design is signed off. A QA gate that cries wolf in week one gets switched off in week two.

1.3The pipeline

Developer pushes to any branch
CI installs dependencies and Playwright browsers
Astro production build
Local production preview server starts
Site crawled once; all modules share that crawl
Pages & SEO → links → images → responsive → interactions → accessibility → cross-browser
Lighthouse CI
Reporter aggregates everything and decides PASS or FAIL
FAIL → job fails → deployment never starts
PASS + push to the default branch → Cloudflare Pages deployment

Two details are worth understanding, because they explain most of the system's behaviour.

Every QA module exits 0. Modules record findings; they never fail the job themselves. A module that crashes records that crash as an error and the rest still run. This means one broken check cannot hide the other thirty-three, and a CI run always produces a complete report.

The reporter is the only gate. qa-reporter.mjs reads every module's output, applies the configured severities, writes the reports and exits 1 if any error exists. There is exactly one place where PASS becomes FAIL.

1.4The severity model

LevelEffectTypical members
ErrorFails the job, blocks deploymentBroken required page, broken internal link, missing form, wrong company name, horizontal overflow, missing H1, accidental noindex, critical accessibility violation, Lighthouse below threshold
WarningVisible in the report, does not blockMissing alt, multiple H1, external link failure, missing canonical, typography or colour drift, oversized image, minor accessibility violation
PassRequirement satisfied—

Every one of the fifty-plus rules can be moved between those levels, or set to "off", from a single severity block in the config. Section 4.12 lists every key. Setting "failOnWarnings": true makes warnings block as well.

3Phase 1 — Local setup

Identical on GitLab and GitHub. Get a clean run on your machine before you push anything — debugging forty findings through a CI log is slow and demoralising, and the local loop takes seconds.

1Create the branch

git checkout main && git pull
git checkout -b setup/qa-cicd

2Install the kit

Run from the root of the Astro project. The . is the target directory.

node /path/to/astro-qa-kit/install-qa.mjs .           # GitHub Actions
node /path/to/astro-qa-kit/install-qa.mjs . --gitlab  # GitLab CI
node /path/to/astro-qa-kit/install-qa.mjs . --both    # both CI files

The installer copies the engine, the CI file, lighthouserc.cjs, playwright.config.mjs and the test suites; adds the qa:* npm scripts; and appends the QA output paths to .gitignore. It never overwrites an existing file — pass --force only when deliberately upgrading a site that already has the kit.

git status --short

Expect scripts/, tests/, lighthouserc.cjs, playwright.config.mjs, the CI file, and a modified package.json and .gitignore.

3Install the dependencies

npm install -D playwright @playwright/test @lhci/cli wait-on wrangler @axe-core/playwright
npx playwright install --with-deps chromium firefox webkit

The browser download is roughly 400 MB and happens once per machine. On Windows and macOS, drop --with-deps; it installs Linux system packages and does nothing elsewhere.

Local shortcut

To skip the browser download while experimenting, run against an installed Chrome or Edge: QA_CHROMIUM_CHANNEL=chrome npm run qa:all. Leave this unset in CI so every run uses the pinned Playwright build.

4Run it against the site

Terminal 1 — build and serve the production output:

npm run build && npm run preview -- --host 127.0.0.1 --port 4321

Terminal 2 — run the suite:

npm run qa:all

While iterating on the config, skip the two slow modules:

npm run qa:all -- --skip lighthouse,crossbrowser

Individual modules are available as npm run qa:core, qa:links, qa:images, qa:responsive, qa:interactions, qa:accessibility and qa:cross-browser. Each writes to qa-results/ and exits 0; npm run qa:report aggregates them and is the only command that can exit non-zero.

SSR sites

astro preview does not work with an SSR adapter. Serve the built output with the adapter's own command instead and point the QA engine at it with QA_BASE_URL.

4Configuration reference

Everything site-specific lives in scripts/qa-config.json. The engine contains no client names and no production URLs, which is what makes the same code reusable across every site you build. Appendix B is the complete default file.

4.1Identity — the highest-value checks

"businessName": "Acme Plumbing",
"businessNameAliases": ["Acme Plumbing Ltd", "Acme"],
"forbiddenBusinessNames": ["Nextkin", "Previous Client Name", "Lorem Ipsum Co"]

forbiddenBusinessNames is the single most valuable field in the file. Fill it with the name of whatever site this one was cloned from, plus any placeholder names your templates carry. The engine scans visible text, <title>, meta description, Open Graph tags, the footer and form regions. A hit is an error, which is exactly right: a leaked client name must never reach production.

businessName missing from a required page is a warning by default, since a legitimate page may not mention it.

4.2Contact details

"phone": "+1 604 555 1234",
"requiredPhone": true,
"email": "hello@acmeplumbing.com",
"emailDomain": "acmeplumbing.com",
"requiredEmail": true

Phone numbers are compared on their last ten digits, so (604) 555-1234, 604.555.1234 and +16045551234 all match. The engine checks both the visible text and the tel: links, and reports three distinct situations: missing entirely (error when required), present as text but with no matching tel: link or vice versa (warning), and a tel: link pointing at a completely different number (warning). The last one catches a very common template-leftover bug.

emailDomain flags mailto: links on an unexpected domain.

4.3Pages

"requiredPages": ["/", "/about/", "/services/", "/contact/", "/privacy-policy/"],
"formPages": ["/contact/", "/request-a-quote/"],
"responsivePages": ["/", "/services/", "/contact/"],
"lighthousePages": ["/", "/about/", "/services/", "/contact/"],
"privacyPolicyUrl": "/privacy-policy/",
"notFoundPath": "/qa-404-probe-do-not-create/"
KeyMeaning
requiredPagesMust return 2xx (redirects allowed). Also seeds the crawl.
formPagesMust contain a valid form.
responsivePagesTested at every viewport. Keep short — this is pages × viewports.
lighthousePagesLighthouse runs here, twice each by default.
notFoundPathA URL guaranteed not to exist. The engine requests it to confirm a real 404 status and an intact 404 page: heading, body content, header, navigation links, footer, no broken images, no overflow.

4.4Selectors and landmarks

"logoSelector": "header a.logo",
"headerSelector": "header",
"footerSelector": "footer",
"navSelector": "header nav",
"formSelectors": ["form", "iframe[src*='leadconnectorhq']", "iframe[src*='hubspot']"],
"formRequiredFields": ["name", "email"]

Open the site and confirm each selector matches before the first run. A wrong logoSelector produces a baffling "logo not found" error on every single run and is the most common setup mistake.

formRequiredFields entries are matched loosely against each field's name, accessible label, placeholder and type, so "email" matches a field named contact_email or labelled "Email address".

Embedded forms

Cross-origin iframes cannot be read into. For GoHighLevel, HubSpot and similar embeds the engine verifies the iframe is present and visible, and scans its title and src for forbidden business names. Field-level checks apply to native <form> elements only.

4.5Viewports and layout rules

"viewports": {
  "mobile":  { "width": 375,  "height": 812  },
  "tablet":  { "width": 768,  "height": 1024 },
  "laptop":  { "width": 1366, "height": 768  },
  "desktop": { "width": 1920, "height": 1080 },
  "wide":    { "width": 2560, "height": 1440 }
},
"design": {
  "containerSelector": ".container",
  "containerMaxWidth": 1280,
  "pageGutterMin": 16,
  "overflowTolerancePx": 2,
  "requiredVisibleSelectors": ["header", "main", "footer", "header nav"],
  "noOverlapSelectors": []
}

At each viewport the engine scrolls the full page to trigger lazy content, then checks:

  • Horizontal overflow — scrollWidth beyond clientWidth past the tolerance, naming the outermost offending elements and their right edge in pixels. Error.
  • Missing elements — anything in requiredVisibleSelectors absent or invisible. Error.
  • Clipped text — text cut off by overflow: hidden without an intentional ellipsis. Warning.
  • Overlap — pairs from noOverlapSelectors covering more than 25% of the smaller element. Warning.
  • Container and gutters — only when containerSelector is set. Warning.

noOverlapSelectors ships empty on purpose: generic overlap detection produces constant false positives. List only elements that must never collide, for example ["header .logo", "header nav"].

Every failed viewport produces a full-page screenshot in qa-results/screenshots/, uploaded as a CI artifact.

4.6Interactions

"interactions": [
  {
    "name": "Mobile navigation",
    "page": "/",
    "viewport": "mobile",
    "trigger": "[data-qa='menu-toggle']",
    "target": "[data-qa='mobile-menu']",
    "expect": "visible",
    "closeAfter": true,
    "optional": false,
    "critical": true
  }
]

Each entry drives one open-and-close test. The engine clicks the trigger, waits for the target to reach the expected state, then presses Escape and, failing that, activates the trigger again to confirm it closes. It also verifies the trigger is keyboard focusable and that no console errors fire during the interaction.

KeyEffect
optionaltrue passes quietly when the trigger does not exist. Use while a component is still being built.
criticalDefaults to true; also runs in the Firefox and WebKit smoke suite.
closeAfterSet false for things that are not meant to close.
expect"visible" or "hidden".

Add one entry per menu, modal, dropdown, accordion, tab set and drawer. If you control the templates, add data-qa attributes and target those — they survive CSS refactors in a way that .nav__toggle--active does not.

Hover and focus states are configured separately:

"states": {
  "enabled": true,
  "pages": ["/"],
  "selectors": ["header nav a", "a.btn", "button[type='submit']"],
  "maxElementsPerSelector": 5,
  "requireFocusIndicator": true
}

For each element the engine snapshots computed styles, hovers, compares, moves the pointer away, focuses, and compares again. No change on hover is a warning; no visible focus indicator is a warning and a genuine keyboard-accessibility problem.

4.7Typography and brand colours

"design": {
  "typography": {
    "body": { "selector": "body", "fontFamily": "Inter", "fontSize": "16px", "lineHeight": "24px" },
    "h1":   { "selector": "h1", "fontFamily": "Inter", "fontSize": "48px", "fontWeight": "700" },
    "nav":  { "selector": "header nav a", "fontSize": "16px" }
  },
  "brandColors": ["#111827", "#2563EB"],
  "colorRules": [
    { "name": "Primary button", "selector": ".btn-primary", "property": "backgroundColor", "expected": "#2563EB" },
    { "name": "Body text", "selector": "body", "property": "color", "expected": "#111827" }
  ]
}

Font families are compared on the first family in the computed stack, so a fallback chain does not cause a false failure. Colours are normalised, so #2563EB, rgb(37, 99, 235) and rgba(37,99,235,1) all compare equal. A rule with no expected falls back to the brandColors palette.

With colorRules empty, colour checking is skipped entirely. Both default to warning; raise them to error once a design is signed off and you want drift to block.

4.8Images

"imageRules": {
  "maxFileSizeKB": 500,
  "requireLazyLoadBelowFold": true,
  "preferModernFormats": false,
  "checkBackgroundImages": true,
  "aspectRatioTolerance": 0.1,
  "maxPages": 50,
  "criticalSelectors": ["header img", "img[alt*='logo' i]", "[class*='hero'] img"]
}

Anything matching criticalSelectors that fails to render is an error; other broken images are a warning by default. Distortion is only reported when object-fit actually allows stretching, which keeps the false-positive rate near zero. Lazy-loading warnings apply only below the fold, so critical LCP images are never flagged. alt="" is accepted as a deliberate marker for a decorative image; a missing alt attribute is not.

4.9Accessibility

"accessibility": {
  "enabled": true,
  "pages": ["/", "/contact/"],
  "tags": ["wcag2a", "wcag2aa", "wcag21a", "wcag21aa"],
  "disableRules": [],
  "errorImpacts": ["critical", "serious"]
}

Violations at an impact listed in errorImpacts become errors; everything else is a warning. The report includes a dedicated accessibility summary with a link to axe's fix guidance for each rule. Lighthouse contributes a second, independent accessibility score on top.

Expectation setting

Automated tooling catches roughly a third of real accessibility problems. Keyboard-only navigation and a screen-reader pass are still worth doing before a launch that matters.

4.10Crawl, runtime noise and timeouts

"crawl": {
  "enabled": true,
  "maxPages": 100,
  "concurrency": 5,
  "checkExternal": true,
  "requireExternalBlank": false,
  "excludePatterns": ["^/admin", "^/api/"],
  "softNotFoundText": []
},
"runtime": {
  "ignorePatterns": ["favicon.ico", "google-analytics", "googletagmanager",
                     "leadconnectorhq", "hubspot", "ResizeObserver loop"]
},
"timeouts": { "navigationMs": 30000, "requestMs": 15000 }

The crawl starts from requiredPages, stays on the current origin, normalises URLs so /about and /about/ are one page, skips mailto:, tel:, javascript: and anchors, and stops at maxPages.

softNotFoundText catches soft 404s: if your 404 page returns HTTP 200 (some hosts do), list a phrase unique to it, such as "Page not found", and the engine will treat pages rendering it as broken.

runtime.ignorePatterns suppresses third-party console noise. These are matched against both the message text and the resource URL, so an analytics script failing to load does not fail your build.

4.11Lighthouse

"lighthousePages": ["/", "/about/", "/services/", "/contact/"],
"lighthouse": {
  "enabled": true,
  "numberOfRuns": 2,
  "performance": 0.75,
  "accessibility": 0.90,
  "bestPractices": 0.90,
  "seo": 0.90
}

Lighthouse CI runs each page numberOfRuns times and the median is used, which absorbs most of the variance from shared CI runners. The reporter reads .lighthouseci/manifest.json and applies these thresholds itself, so Lighthouse failures appear in the same report as everything else rather than failing the job separately.

Add "preset": "desktop" to score against the desktop profile instead of the default mobile one.

5Getting to a clean first run

The first run on a real site will produce findings. That is the point. The work is deciding, for each one, which of three things it is.

The finding is…Action
A real bugFix the site. This is the system doing its job.
A real rule you are not ready to enforce yetMove it to "warning" or "off" in severity, with a note to revisit.
A misconfigurationFix qa-config.json — usually a selector that does not match.

What not to do is disable rules wholesale to get to green. The following seven are the ones that actually prevent embarrassment, and should stay at error from day one:

RuleWhat it stops reaching production
forbiddenBusinessNameAnother client's name on this client's site
internalLinkNavigation to a page that does not exist
missingFormA contact page that cannot capture a lead
brokenRequiredPageA core page returning 404 or 500
horizontalOverflowA site that scrolls sideways on a phone
seoNoindexA staging noindex shipped to production
privacyPolicyA site with no reachable privacy policy

A reasonable day-one starting point

"severity": {
  "accessibilityMinor": "off",
  "lazyLoading": "warning",
  "typography": "warning",
  "externalLink": "off"
}

Target zero errors. Carrying warnings is fine and expected — they are the backlog.

Expect a second round in CI

CI is a different machine. Different fonts, a slower Lighthouse, a cold cache. A few new findings on the first CI run is normal, not a sign that something is wrong. Fix or tune, push again.

6Phase 2A — GitLab implementation

The engine has nothing platform-specific in it, so GitLab is a good place to trial the system before committing to it everywhere. Only .gitlab-ci.yml differs from the GitHub setup.

5Add the CI/CD variables

Settings → CI/CD → Variables → Add variable, three times:

KeyValueFlags
CLOUDFLARE_API_TOKENScoped token (section 8)Masked, Protected
CLOUDFLARE_ACCOUNT_IDFrom Workers & Pages → OverviewMasked, Protected
CLOUDFLARE_PROJECTPages project name, exactlyProtected
Do this before you push

Protected restricts a variable to jobs running on protected branches. Without it, a merge request from a feature branch or a fork can read your Cloudflare token. Protect the branch first (next step), then the variables work on main and nowhere else.

Leave CLOUDFLARE_PROJECT unmasked — masking imposes length and character rules that project names often fail, and the name is not sensitive.

6Protect the default branch

Settings → Repository → Protected branches

  • Branch: main
  • Allowed to push: No one
  • Allowed to merge: Maintainers, or Developers + Maintainers
  • Allowed to force push: off

Settings → Merge requests

  • Enable Pipelines must succeed
  • Optionally, All threads must be resolved

"Pipelines must succeed" is GitLab's equivalent of a required status check. Because the reporter exits 1 on any error, a failing QA run fails the job, fails the pipeline and blocks the merge.

7Push and inspect

Push the branch and open a merge request. Check three places:

  • CI/CD → Pipelines — the qa job runs. The deploy job does not appear for a merge request.
  • The merge request page — a test summary listing every check, from the JUnit report. Errors appear as failures, warnings as skipped.
  • Job → Browse artifacts — qa-report.md, screenshots, Lighthouse HTML.

Runner notes

The pipeline needs a Docker-executor runner, which is the default on GitLab.com shared runners. It uses node:20-bookworm and installs Playwright browsers with --with-deps, caching them in .playwright/ keyed on package-lock.json. Expect 8–15 minutes for a first run and 4–8 minutes afterwards.

A faster image. Microsoft's Playwright image ships the browsers preinstalled:

variables:
  NODE_IMAGE: "mcr.microsoft.com/playwright:v1.49.0-noble"

Then delete the npx playwright install line. The image tag must match the Playwright version in your package-lock.json, or you get a confusing "Executable doesn't exist" error. If you would rather not track that, keep the default.

Shared runner minutes. On GitLab.com's free tier, running Playwright and Lighthouse on every push to every branch consumes compute minutes quickly. To trial it more cheaply, narrow the trigger:

qa:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

Self-hosted runners have no such limit; run it on everything.

Manual approval before production

GitLab's protected environments feature requires Premium. On Free, make the deploy job manual so a person clicks to release:

deploy:
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $CI_PIPELINE_SOURCE == "push"
      when: manual

7Phase 2B — GitHub implementation

Everything tuned on GitLab carries over unchanged. In each repo you swap the CI file, move three variables and replace the branch rules.

5Open the pull request and watch the first run

GitHub → Pull requests → New pull request → base main, compare setup/qa-cicd.

In the Actions tab, the QA and Deploy run executes the Website QA job. The Deploy to Cloudflare Pages job shows as skipped — correct, because pull requests never deploy.

If the run is blocked

Organisations often restrict which actions may run. Fix at Settings → Actions → General → Actions permissions, allowing at minimum actions/checkout, actions/setup-node, actions/cache and actions/upload-artifact.

6Read the results

  • Job summary — bottom of the run page. The whole qa-report.md renders there, tables and all. This is the link to send a project manager.
  • Annotations — errors and warnings appear inline at the top of the run and against the pull request.
  • Artifacts — qa-report-<run id>, containing the reports, screenshots, Lighthouse HTML and preview.log. Uploaded even when QA fails.

Enable: Require a pull request before merging; Require status checks to pass → Add checks → Website QA; Block force pushes.

Ordering matters

Website QA only appears in the status-check picker after it has reported at least once. Run the pull request first, then create the ruleset. The name comes from the job's name: in the workflow — if you rename the job, update the ruleset or the rule silently stops protecting anything.

9Optional — require a human for production

Settings → Environments → production → Required reviewers. The deploy job already runs in the production environment, so adding reviewers means every production deploy waits for a named person to approve, even after QA passes. Worth it for a high-stakes site; unnecessary friction for a brochure site.

8Phase 3 — Cloudflare

Create the Pages project

If the site is already on Cloudflare Pages, note the exact project name — it is case-sensitive. Otherwise create a Direct Upload project. Do not connect it to Git; the pipeline does the deploying.

npx wrangler pages project create acme-plumbing --production-branch=main

Create a least-privilege API token

Cloudflare dashboard → My Profile → API Tokens → Create Token. Use the Edit Cloudflare Workers template, or build a custom token with:

  • Permissions: Account → Cloudflare Pages → Edit
  • Account Resources: Include → your account only

Copy it immediately; Cloudflare shows it once.

Never use the Global API Key

It grants full access to every zone on the account and cannot be scoped down. A scoped Pages token can do exactly one thing: deploy to Pages.

Find the account ID

Workers & Pages → Overview; the Account ID is in the right-hand sidebar. It is also the hex string in the dashboard URL after dash.cloudflare.com/.

Prevent double deployment

The step people skip

If Cloudflare Pages is connected directly to the repository — it supports both GitHub and GitLab — Cloudflare builds and deploys on its own whenever the default branch changes, without ever looking at your QA result. You would have a gate that blocks nothing while appearing to work.

Option A — CI owns production (recommended). Cloudflare dashboard → Workers & Pages → your project → Settings → Builds & deployments → Disconnect the Git integration. The project, its custom domain and its deployment history all remain; only the automatic Git build stops. wrangler pages deploy keeps working through the Direct Upload path. From that point nothing reaches production without passing QA.

Option B — Cloudflare owns production, QA stays advisory. Keep the Git integration, delete the deploy job, and rely on branch protection: QA must pass before a merge, and only merges trigger Cloudflare's build. Weaker, because an admin pushing straight to the default branch bypasses QA entirely. Choose this only if something else depends on Cloudflare's own build pipeline.

Output directory

The deploy step runs wrangler pages deploy dist. If astro.config.mjs sets a different outDir, change dist in the CI file to match.

10Day-to-day workflow

Developer branches and pushes
QA runs automatically — every branch, every push
Fail — developer reads the report, fixes, pushes again
Pass — the merge/pull request can be reviewed and approved
Merge to the default branch
QA runs again on the merged result
Pass → Cloudflare production deployment
Fail → deployment never starts
The rule

QA runs on every push. Deployment does not. Production deploys only from the default branch, and only after QA passes.

Who reads what

RoleLooks at
DeveloperThe annotations or merge-request test list; screenshots for layout failures; the full job log only when something is genuinely odd
ReviewerThe status check or pipeline result — it is binary, and it blocks the merge
Project managerqa-report.md in the job summary or artifacts: plain-language tables of what passed, what warned and what failed

11Rolling it out across every site

A CI definition has to exist inside each repository — neither GitHub nor GitLab will run a pipeline that is not in the repo. But "a file" can mean fifteen lines rather than twenty files.

For a team running many client sites, the central kit repo is the right answer. Each site repo then holds only:

.github/workflows/qa.yml   (or .gitlab-ci.yml)   ~15 lines, calls the shared definition
scripts/qa-config.json                            the client's name, phone, pages, selectors
Why this works without code changes

The engine resolves every path from the current working directory, and Node resolves import 'playwright' relative to the importing file. So the shared engine can be checked out into .qa-engine/ and run against the site at the repo root — and the QA dependencies stay in the kit repo, leaving each client's package.json untouched. Nothing in scripts/ needs to change to move between models.

Two things to arrange first:

  • GitHub: if the kit repo is private, set Settings → Actions → General → Access on it to allow access from other repositories in the organisation, and give the calling workflow a token that can check it out.
  • GitLab: use include: project: pointing at the kit project; the same visibility consideration applies.

Until then, each additional site is

git checkout -b setup/qa-cicd
node /path/to/astro-qa-kit/install-qa.mjs .
npm install -D playwright @playwright/test @lhci/cli wait-on wrangler @axe-core/playwright

Then edit qa-config.json, add the three variables, set the branch rules, and merge. The engine files are byte-identical across every site; only the config differs.
