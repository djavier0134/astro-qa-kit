1What this thing actually does

Think of it as a very thorough, very fast assistant who checks every page of a website before a client ever sees it — and who is allowed to say "no, this isn't going live yet."

The problem it solves

Most things that embarrass a web team on launch day are not clever or subtle. They are things like:

  • A link that goes to a page that no longer exists
  • A photo that doesn't load
  • The previous client's business name still sitting in the footer, because this site was copied from theirs
  • The contact form quietly disappearing during a redesign
  • A page that scrolls sideways on a phone

Every one of these is findable by a machine. They get missed because checking twenty pages across five screen sizes by hand is dull work, and dull work gets skipped when a deadline is close.

In one sentence

It builds your website, opens it in real web browsers, clicks around, and refuses to let a broken version go live.

What it checks

Thirty-four checks, grouped into seven areas:

AreaIn plain English
Pages & search Do the important pages load? Does each one have a title and description so Google can list it properly? Is the "page not found" page intact?
Identity Is the right business name on the site? Is the wrong one anywhere? Are the phone number and email correct, and clickable?
Forms Does the contact form still exist, and does it have the fields it needs?
Links Does every link actually go somewhere?
Images Do the pictures load? Are any stretched out of shape or enormous?
Layout Does the page look right on a phone, a tablet and a desktop? Anything overlapping, cut off, or sliding off the side?
Clicking & accessibility Do menus open and close? Can someone using only a keyboard get around? Is the text readable against its background?

What it does not do

It doesn't judge whether the design is nice, whether the writing is any good, or whether the site does what the client wanted. It checks that things work, not that they are right. A human still has to look at it.

How it fits into the day

Someone changes the website and saves their work to GitHub
The robot wakes up automatically and starts checking
Finds something broken → the website does not go live
Everything fine → the website goes live by itself

Nobody has to remember to run it. That's the whole point.

2Before you start

What you need

ThingWhy
An Astro website in GitHubThis is the website's filing cabinet, stored online
Admin access to itYou'll need to change settings, not just files
Node.js version 22 or newerThe software that runs the checks. Free
About 2 hours, onceOnly for the first site. Later ones take minutes
Check your Node version first

Open a terminal and type node --version. If it says anything lower than v22, install a newer one from nodejs.org before going further. Astro refuses to build on older versions, and you'll waste time wondering why.

One thing to find out before you begin

Open your website's folder and look for where package.json lives. There are two common shapes:

ShapeWhat it means for you
package.json at the top The simple case. Follow the steps exactly as written
package.json inside a site/ folder Very common at Goodly. You'll need one extra step — see the box in section 3

3Setting it up, step by step

1Get the kit onto your computer

You only ever do this once. It puts a copy of the checking tools on your machine.

git clone https://github.com/djavier0134/astro-qa-kit.git

Remember where it lands — you'll point at this folder from every site.

2Make a safe space to work in

Never do setup work directly on the live version. Make a "branch" — a private copy you can experiment in without anyone noticing. 

git checkout -b setup/qa-cicd
3Copy the kit into your website

From inside your website's folder:

node /path/to/astro-qa-kit/install-qa.mjs .

If your package.json is inside a site/ folder, use site instead of the dot: 

node /path/to/astro-qa-kit/install-qa.mjs site
Important if you used site

The installer will put a file at site/.github/workflows/qa-deploy.yml. That is the wrong place. GitHub only looks for these files at the very top of the project, so if you leave it there, the checker will never run at all — and everything will look fine, because there will be no errors. Move it up: 

mkdir -p .github/workflows
mv site/.github/workflows/qa-deploy.yml .github/workflows/

Then open that file and ask a developer to add working-directory: site to it. This is the single most common way to end up with a checker that silently does nothing.

4Install the extra tools

These are the robot's eyes — real web browsers it can drive.

npm install -D playwright@1.57.0 @playwright/test@1.57.0 @lhci/cli wait-on wrangler @axe-core/playwright
npx playwright install chromium firefox webkit

That second command downloads about 400 MB. It only happens once per computer.

If you're on Windows and the download fails

Some networks can't reach the servers these browsers come from. You don't need to fix it — just tell the checker to use the Chrome you already have installed. See section 5.

4Telling it about your website

This is the only part that's different for each site, and it's the part worth taking your time over. Everything else is identical everywhere.

Open the file scripts/qa-config.json. It's a list of settings. Change the values between the quote marks; leave the rest alone.

The business details

"businessName": "Ammons Awnings & Handrails",
"businessNameAliases": ["Ammons Awnings", "Ammons"],
"forbiddenBusinessNames": ["Some Other Client", "Lorem Ipsum"],

"phone": "912-261-1069",
"email": "hello@example.com",
"emailDomain": "example.com",
The most valuable setting in the whole file

forbiddenBusinessNames. Because sites get copied from one another, the previous client's name sometimes survives into the new site. Put the names of your other clients here. If one of them ever shows up on this website, the checker stops everything immediately. This single setting prevents the most embarrassing mistake in the business.

Which pages matter

"requiredPages": ["/", "/about", "/services", "/contact", "/privacy-policy"],
"formPages": ["/contact"],

These are the pages that must work. If any of them fails to load, nothing goes live.

Slashes matter more than you'd think

Some sites use /contact and some use /contact/ — with a slash at the end. These are treated as different addresses, and using the wrong one gives you a page-not-found error for a page that is perfectly fine. Open the real website, look at the address bar, and copy whichever form it uses.

Where things are on the page

"logoSelector": "header a.brand",
"headerSelector": "header",
"footerSelector": "footer",

These tell the checker where to find the logo, the top bar and the bottom bar. A developer can read these off the site in a couple of minutes. If they're wrong, you'll get confusing "logo not found" messages on every single page.

Leave these alone at first

design.colorRules, design.noOverlapSelectors and visualRegression all start switched off deliberately. Turn them on later, once the design is signed off. Turning them on early means spending your first week chasing complaints about things that aren't actually wrong.

5Running it on your own computer

Do this before you upload anything

Get it working on your own machine first. Checking on your computer takes seconds. Checking online takes about eight minutes each time. Finding your first forty problems eight minutes at a time is a miserable afternoon.

You need two terminal windows.

Window one — start a local copy of the website and leave it running:

npm run build
npm run preview -- --host 127.0.0.1 --port 4321

Window two — run the checks:

npm run qa:all

While you're still fixing things, skip the two slowest checks:

npm run qa:all -- --skip lighthouse,crossbrowser
On Windows, if it says "Executable doesn't exist"

It couldn't download its own browser. Tell it to borrow Chrome instead. In PowerShell: 

$env:QA_CHROMIUM_CHANNEL="chrome"; npm run qa:all -- --skip lighthouse,crossbrowser

Only do this on your own computer. The online version downloads its browsers without trouble.

Where the results appear

FileWhat's in it
qa-report.mdThe readable report. Start here
qa-results/screenshots/Pictures of any page that looked wrong

6How to read the results

Every finding is one of three things:

LabelWhat happensWhat it means
ErrorNothing goes live Something is genuinely broken. Fix it
WarningSite still goes live Worth looking at, not urgent
Pass— That check was fine

Only errors stop a release. You can have fifty warnings and still go live. That's deliberate — if warnings blocked things, you'd never ship anything.

What to do with each finding

If the finding is…Then
A genuine problem with the siteFix the website
A real rule you're not ready to enforce Change it to "warning" in the settings
The checker misunderstanding something Fix the settings file, not the website
Rules worth keeping strict from day one

Wrong business name, broken internal links, missing contact form, a required page that won't load, a page that scrolls sideways on a phone, a page accidentally hidden from Google, and a missing privacy policy. These are the ones that cause real damage.

Aim for zero errors, not zero warnings

Zero errors is the goal. Carrying warnings is completely normal and nothing to feel bad about. Resist the urge to switch rules off just to get a clean screen — a checker that's been quietened into silence protects nobody.

7Turning on the lock

Up to now the checker reports problems but can't actually stop anything. This is where you give it teeth.

1Upload your work
git add .
git commit -m "Add automatic website checking"
git push -u origin setup/qa-cicd

Then on GitHub, open a "pull request" — a request to merge your work in.

2Watch it run

Go to the Actions tab. You'll see it working through the checks. Scroll to the bottom of the page for the full report.

First time online usually turns up a few new things. Different computer, slightly different results. Normal.

3Lock the main version

Settings → Rules → Rulesets → New branch ruleset. Name it Protect main, set it to Active, target the default branch, and tick:

  • Require a pull request before merging
  • Require status checks to pass → choose Website QA
  • Block force pushes
Can't find "Website QA" in the list?

It only appears after the check has run at least once. Let step 2 finish, then come back.

The step people skip — and it undoes everything

If your hosting (Cloudflare Pages) is connected directly to GitHub, it builds and publishes the site by itself whenever the main version changes — without ever looking at the checker's verdict. You would have a lock on the front door and an open window beside it. Either disconnect that direct connection and let the checker handle publishing, or accept that the checker is only giving advice. Ask a developer which applies to your site.

8Proving it actually works

Don't trust a safety net you've never watched catch anything. Break things on purpose, on your branch, and check it notices. Put each one back afterwards.

Break this on purposeYou should see
Add a link to a page that doesn't existError naming the bad link
Point a photo at a missing fileError naming the image
Delete the contact formError: required form not found
Put another client's name on a pageError naming the word and the page
Add something very wide to a pageError on phone and tablet, plus a screenshot
Break the mobile menu buttonError: the menu didn't open
On a real client's website

Only ever do these on your own branch, never on the live version — and only after the hosting question in section 7 is settled. Otherwise you risk publishing a deliberately broken site to a real customer.

9Things that go wrong, and what to do

What you seeWhat's happening
Checks never run at all, no errors anywhere The workflow file is in the wrong folder. See the red box in section 3. This is the dangerous one, because it looks like success
Node.js v20 is not supported by Astro Node is too old. It needs version 22 or newer
Pages you know exist are reported as missing Almost always the trailing-slash problem in section 4
Executable doesn't exist Browsers didn't download. On Windows, use the Chrome workaround in section 5
You fixed something, but the same error keeps appearing You're probably looking at an old run, or pressed "Re-run jobs" on one. Re-running re-tests the old version. Check the run matches your newest change
Dozens of accessibility complaints Normal on an older site. Set accessibilityMinor to "off", deal with the serious ones first
Performance scores wobble between runs Shared machines vary. Lower the threshold slightly, or raise the number of runs so it takes an average
The site went live even though checks failed The hosting is still publishing on its own. Go back to the red box in section 7

If you remember nothing else

Get it working on your own computer before uploading. Only errors stop a release. And check that your hosting isn't publishing the site behind the checker's back — otherwise none of this protects you.
